# 실거래 조회 범위·속도 개선 (2026-11-08)

## 실제 원본 확인
기존 저장소 MOLIT 인증으로 `RTMSDataSvcNrgTrade`의 광명시 202610, 202609, 202608 각 한 페이지(1000행)를 요청했다. 세 요청 모두 HTTP 200 / 000 OK다. 광명시 원본 12/17/9건 중 광명동은 2/7/3건이며 정확히 공개된 158-217 일치 행은 이 세 달에서 확인되지 않았다. 같은 법정동 12개 원본 행 중 일반건축물 5행은 `1**` 또는 `3**`로 지번이 가려졌다. 해당 자료가 158-217이라는 뜻도, 해당 필지에 과거 거래가 없다는 뜻도 아니다.

`RTMS_COMMERCIAL_DISCLOSURE_20261108.json`은 원본 응답의 공개 속성만 기록한 진단 결과다. 이 파일은 취소 여부 등 모든 원본 필드를 보존하지 않으므로 운영 거래 캐시로 사용하지 않는다. 브라우저 회귀 테스트에서 공개 지번 처리 검증에만 사용한다.

## 운영 변경
- 기본값을 저장된 거래로 변경했다. 필지를 열기만 하면 국토부 월별 API를 호출하지 않는다.
- 기존 all 값도 저장 자료 조회로만 해석한다. 251개월 작업 큐를 만들지 않는다.
- 기간을 직접 선택하면 최대 3개월씩 조회한다. 각 요청 8초, 한 묶음 12초 제한을 적용한다. 실패·중단 시 성공 결과는 유지한다.
- 미확인 거래를 0건으로 표시하지 않는다. 공개 지번이 없는 거래는 비교용으로 구분하고 동일 필지로 추정하지 않는다.
- 같은 법정동 비교는 반경 기반 주변거래와 구별한다. 사용자 버튼 클릭으로만 비교조회한다.
- 성공한 지역·유형·월 자료만 1시간, 최대36개월/1.5MB 한도로 브라우저 캐시에 보관한다. 전국 필지 대장 복제나 별도 전국 수집 서버는 없다. 키를 캐시에 넣지 않는다.
- 광명동 158-216의 원본 확인 3건은 기존처럼 표시한다. 다른 지번에 재사용하지 않는다.

## 필지·기간 단일 요청 연결부
`parcel-history-provider.mjs`와 로컬 서버의 POST `/api/transactions/parcel`을 추가했다. 빅밸류 공식 `/realdeal/pnu` 계약에 맞춰 PNU/계약시작일/종료일을 한 번의 요청으로 보낸다. 인증 토큰과 가격 단위를 확인한 경우에만 작동한다.
- 서버 전용 `BIGVALUE_JWT`, `BIGVALUE_PRICE_UNIT=won|manwon` 필요. 단위는 계약된 상품 응답으로 검증해야 한다.
- 웹과 다른 서버에 배포할 경우 `PARCEL_HISTORY_ALLOWED_ORIGINS`에 운영 웹 origin을 명시한다. 서버 route는 최대20회/분으로 제한한다.
- Pages 빌드 환경의 `PARCEL_HISTORY_ENDPOINT`는 해당 서버의 HTTPS URL만 받는다. JWT는 절대로 Pages 설정이나 클라이언트 파일에 넣지 않는다.
- 이 작업에서는 신규 유료 계약·토큰 발급·서버 신규 배포를 하지 않았다. 운영 Pages의 일괄조회 endpoint는 비어 있으므로 실제 빅밸류 조회가 활성화됐다고 주장하지 않는다.
- 결과 PNU/유형/계약일·취소 여부를 검사한다. 전체 이력 완전성은 계약 검증 없이 true로 만들지 않는다. 공급처 실패 시 월별 전체검색으로 되돌아가지 않는다.
- 현재 commercial 상품에 전유/건물 면적이 누락된 행은 임의로 토지면적으로 바꾸지 않고 제외한다. 계약 상품의 반환 필드가 확정되면 이 매핑 검증이 필요하다.

## 검증
행동 테스트에서 초기 API 0회, 명시적 조회 최대3개월, 429 첫 실패 중단, 다른 필지의 월 캐시 재사용, 마스킹 지번 배제, 저장3건 유지, PNU 연동 1회 호출 및 실패 시 월순회 금지를 검증한다. 실제 공급처 인증 응답은 위 국토부3개월 진단만 수행했으며 빅밸류는 모의 응답 기반 계약 테스트다.
