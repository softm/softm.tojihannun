# 토지한눈 분산 데이터 저장소 설계

## 용량 정책

- 저장소당 GitHub Pages 게시 산출물 최대 **1,000,000,000 bytes (1GB)**.
- **900,000,000 bytes (900MB)** 도달 전에 새 저장소로 분할한다.
- 1GB 이상이 예상되면 **배포를 차단**한다. 파일 크기만이 아니라 Pages에 게시할 모든 파일(인덱스·매니페스트·정적 파일 포함)의 합계로 계산한다.
- Git 저장소의 히스토리 크기와 Pages 게시 용량은 별도로 측정한다. Git 이력 누적과 GitHub Actions 제한도 관리한다.
- 중앙 설정: `data/transactions/storage-registry.json`.

## 데이터 분할

1. 시군구 코드 → 거래 유형 → 계약 연도 → 계약 월 순으로 분할한다.
2. 저장소 이름은 `softm/realestate-data-001`부터 3자리 연속 번호를 사용한다.
3. 한 시군구가 여러 저장소에 걸치면 중앙 인덱스에 **복수 shard**를 기록한다. 시군구 코드만으로 단일 저장소를 결정하지 않는다.
4. 변경된 구간만 다시 게시하고, 매번 모든 저장소를 배포하지 않는다.
5. 공개 JSON은 원본 데이터 수집 상태와 구분한다. 미수집·API 오류를 거래 0건으로 취급하지 않는다.

## 안전한 전환 순서

1. 기존 JSON과 수집 체크포인트를 백업하고 건수·해시·게시 용량을 측정한다.
2. 새 저장소를 생성하고 각 저장소에 Pages 및 필요한 Actions 권한·Secrets를 구성한다.
3. 지역별 데이터 이전 및 정합성 검증 후, 해당 지역의 새 수집기를 기존 체크포인트에서 재개한다.
4. 중앙 인덱스의 새 주소로 조회 테스트를 완료한 후 토지한눈/토지이용한눈 조회를 전환한다.
5. 중복 수집 방지를 위해 구간별 수집 책임을 단일 워크플로로 이관한다.
6. **검증 전 기존 JSON 삭제 금지.** 검증 후 별도 커밋에서 제거한다.

## 현재 상태

이 문서는 **용량·분할 설계**이며 신규 저장소 생성, 실제 수집기 이전, Pages 분산 배포를 완료했다는 뜻이 아니다. `storage-registry.json`의 `planned` 상태를 유지한다.

## 운영상 제한

GitHub Pages를 여러 개로 나누더라도 GitHub의 Pages 이용 정책, 사이트 크기, 대역폭 및 Actions 제한은 계속 적용된다. 1GB는 보장된 실사용 가능량이 아니라 배포 계획상의 절대 상한이다.
